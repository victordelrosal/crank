## Adopted: ten deltas

**D1. Name the three layers once, and Crank's place in them.**
Harness = the environment (tools, filesystem, permissions, model routing, budget, logging).
Loop = the feedback cycle (generate, act, evaluate, decide). Graph = the topology (which node
runs next, what fans out, what joins, where the gates are). They nest: the harness contains the
graph, the graph contains loops. Crank is a loop skill whose DECOMPOSE step is its graph step; the
harness is Claude Code's, and Crank specifies what it needs from it rather than building one. Say
this once, plainly, and use it as a diagnostic rather than a taxonomy to worship.
Source: beamnxw (three-layer framing); LangChain's "agent = model + harness" via the same article.

**D2. Which layer owns the failure (new diagnostic).**
A stuck round is usually answered with another round when it should be answered at a different
layer. The table: cannot reach the data / lost its state / too much access -> harness. First
attempt close but unreliable / spins forever / declares done without proof -> loop. Specialists
running in the wrong order / cannot tell which stage broke / work waiting on nothing -> graph.
Workflow changing every run -> stop formalizing, simplify the harness.
Source: beamnxw (symptom table).

**D3. The fake-edge test (DECOMPOSE).**
For each ordered pair in the plan, ask one question: does B consume an artifact A produced? If
not, the edge is imaginary and the wait is pure latency. Most linear plans carry two or three
fake edges, and a plan of N sequential steps has N points of sequential failure it did not need.
Conversely, if no two workstreams have zero edges between them, there is no fan-out to build: it
is a single loop, and a single loop is fine. This is the graph-fitness check, sibling to the
existing loop-fitness check in FRAME.
Source: Kopadze sections 3, 4, 8.

**D4. The node contract (DECOMPOSE).**
Every dispatched agent gets a bounded job, a defined input, and a defined output shape, declared
before dispatch. A builder whose output is free prose is a node only a human can consume, so the
next stage guesses. Where the harness supports it (Workflow's `agent({schema})`), the output
schema is enforced and the model retries on mismatch. This completes the existing three-line
readback: the readback proves the node understood the brief, the contract proves the next node can
read the result.
Source: Kopadze section 2 (node contract); OpenAI Agents SDK structured output, via beamnxw.

**D5. Reduce in code, not in tokens (the diamond).**
Name the pattern Crank's fan-out already is: fan out (independent workstreams) -> reduce (dedupe,
merge, count, filter, in plain code with no model call) -> verify (a fresh cold skeptic per
finding) -> synthesize (one agent writes the answer from what survived). The reduce step is where
most token waste hides: a model asked to dedupe a list is doing what five lines of code do
exactly, and worse. Consistent with the existing scripts-before-verifiers rule.
Source: Kopadze section 5.

**D6. Layered fan-in (context collapse).**
Never pour every workstream's raw output into one synthesis step. Batch, summarize each batch,
then combine the summaries. Extends the existing cap-the-verifier's-payload rule from
verification to integration and to the handoff itself.
Source: Kopadze section 7.1.

**D7. Hidden edges and isolation (false independence).**
Two workstreams whose briefs never mention each other are still coupled if they write the same
file, branch, database, or rate-limited API. That is a hidden edge, and parallelising across it
produces overwrites nobody logged. At DECOMPOSE, audit shared *resources*, not only shared data;
where two builders must touch the same tree, give each its own git worktree
(`isolation: 'worktree'`) or serialize them with a real edge.
Source: Kopadze section 7.2 (the Bun team's shared-workspace overwrite).

**D8. The fan-in guard: no silent node failure (hard rule).**
In a chain, a dead step stops everything and you notice. In a fan-out, one dead agent among twenty
is a gap in a report that looks complete. So every fan-in asserts its count: compare results
returned against agents dispatched, and when they differ, name the gap in `LOG.md` and in the
handoff, and never let a synthesizer or a verifier grade a partial set as though it were whole.
`.filter(Boolean)` without a count assertion is Crank's honesty doctrine leaking out through a
convenience method.
Source: Kopadze section 7.3; enforces Crank's existing Honesty rubric dimension.

**D9. Anchors: topology does not buy truth (hard rule).**
A fleet where every node's evidence is another node's report is one loop in a costume: internally
consistent, entirely unverified, and more expensive. Every criterion must eventually rest on an
anchor, something that cannot argue back: a test that actually ran, a URL that actually returned
200, a file that exists at the path, a number that came from the environment rather than from an
agent. Adding verifiers adds confidence, not truth. When no anchor is available for a criterion,
say so and mark it judge-checkable instead of dressing a consensus up as a fact. Extends
environment-checkable-over-judge-checkable and the frozen evaluation surface.
Source: Kopadze section 9.

**D10. Do not formalize the topology before you have watched the work.**
Traces from a simpler run tell you where the real edges are. A graph drawn from imagination
freezes assumptions nobody earned, and the more nodes it has the more confidently it is wrong.
First run: one director, a small fleet, good logging. Formalize into a repeatable pipeline only
the paths that proved stable.
Source: beamnxw (mistakes section); Kopadze section 8.

**D11. Reach for Workflow when the topology is real, and price it honestly.**
Crank's default dispatch is parallel Agent calls, correct for a handful of independent
workstreams. Reach for the Workflow tool when the run has genuine topology: many items through
multiple stages, per-item verification, a budget ceiling to enforce in code, or resume after a
crash. Prefer `pipeline()` over a barrier; a barrier earns its latency only when a stage genuinely
needs every prior result at once (dedup across the whole set, an early exit on zero, a comparison
across findings). Price it honestly: fan-out buys breadth, not judgment, and it bills for the
breadth. The public heavy-fan-out data point, as reported by Kopadze and NOT independently
verified this run, is the Bun runtime rewrite: roughly 535,000 lines translated in about eleven
days across about 50 workflows with up to 64 concurrent agents, at roughly $165,000 in usage,
with a human designing and watching throughout.
Source: Claude Code Workflow tool contract (VERIFIED in-harness); Kopadze sections 10 to 12
(figures UNVERIFIED, attributed, never stated as Crank's own finding).

## Rejected, with rationale

**R1. "Graph engineering" as a third Crank mode.** Crank already runs a graph at DECOMPOSE.
A separate mode would be ceremony, and the source articles' own best advice is not to formalize
topology early. Adopt the mechanics, refuse the new mode.

**R2. The three-layer taxonomy as an authority.** Useful lens, vendor-shaped sourcing, and a
closing section incoherent enough to read as unedited generation. Keep the diagnostic, drop the
reverence, and say so in the capture.

**R3. "Most people use AI at 5 to 10 percent" and "the skill behind real roles at large
companies".** Unverifiable engagement copy. Nothing in Crank rests on it.

**R4. Dozens-of-nodes-per-run as a default scale.** Crank's default stays a small sharp fleet.
The volume-as-a-proxy-for-value anti-pattern and the scheduled-mode budget ceiling both stand
unchanged.

**R5. "A graph of loops where cycles watch and correct each other" as the upgrade path.** That is
precisely what D9 warns against when the cycles only ever read each other's reports. Verifier
chains without anchors are a more expensive way to be confidently wrong.
